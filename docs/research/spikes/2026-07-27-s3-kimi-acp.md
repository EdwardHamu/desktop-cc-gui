## 2. ACP Capability Matrix（9 问逐条）

### Q1. ACP 启动方式与 transport — PASS

- `kimi --help` 全部子命令：`export`、`provider`、`acp`、`server`、`web`、`login`、`doctor`、`vis`、`migrate`、`upgrade|update`。
- **`kimi acp` 是独立子命令**（非 `--acp` flag），help 原文："Run kimi-code as an Agent Client Protocol (ACP) server over stdio." 唯一选项是 `--login`（device-code 登录后即退出，供 terminal-auth 用）。
- transport 实测为 **stdio newline-delimited JSON-RPC**：每行一个完整 JSON-RPC message，stdout 无 banner/日志噪声（transcript 首行即 initialize 响应）。harness 按行 `JSON.parse` 全程零解析失败。
- 证据：`evidence/probe1-initialize.transcript.ndjson`。

### Q2. initialize 握手 — PASS

请求 `protocolVersion: 1` + `clientCapabilities.fs` + `clientInfo`，响应逐字段：

```json
{
  "protocolVersion": 1,
  "agentCapabilities": {
    "loadSession": true,
    "promptCapabilities": { "image": true, "audio": false, "embeddedContext": true },
    "mcpCapabilities": { "http": true, "sse": true },
    "sessionCapabilities": { "list": {}, "resume": {} }
  },
  "authMethods": [{
    "id": "login", "type": "terminal", "name": "Login with Kimi account",
    "args": ["--login"],
    "_meta": { "terminal-auth": { "command": "/opt/homebrew/bin/kimi", "args": ["login"] } }
  }],
  "agentInfo": { "name": "Kimi Code CLI", "version": "0.27.0" }
}
```

- `loadSession: true`（Q5 关键前提）、`image: true`、`embeddedContext: true`、`audio: false`。
- `sessionCapabilities.list / resume` 为非标扩展（ACP 草案能力），实测两者均可用（见 Q5 补测）。
- `authMethods` 是 Kimi 的 terminal-auth 扩展：client 可用 `kimi acp --login` 或 `kimi login` 完成 device-code 登录。本机已登录，未实测 authenticate 流程。
- 证据：`evidence/probe1-initialize.transcript.ndjson`。

### Q3. session/new — PASS

- 参数：`{ cwd, mcpServers: [] }`，cwd 生效（session/list 回显同一 cwd）。
- 响应 shape：`{ sessionId: "session_<uuid>", configOptions: [...] }`。sessionId 与 Kimi 磁盘 session（`~/.kimi-code/sessions/`、`session_index.jsonl`）同源，与 mossx 现有 `kimi:<session_*>` canonical identity 约定天然兼容。
- `configOptions` 三个 select：**model**（3 个 alias）、**thinking**（on）、**mode**（default/plan/auto/yolo，含 description）。
- session/new 后异步到达 `available_commands_update` notification（slash commands 清单，含 Kimi 内置 skill）。
- 证据：probe1 transcript。

### Q4. session/prompt lifecycle — PASS

trivial prompt（"Reply with exactly one word: PONG"）：

- notification 序列：`available_commands_update`(1) → `agent_thought_chunk`(17) → `agent_message_chunk`(2) → response。
- **response 只含 `{ "stopReason": "end_turn" }`，不含任何内容**；全部内容经 `session/update` 流式推送。
- tool turn（"用工具列出当前目录文件"，yolo mode）序列：`config_option_update` → `agent_thought_chunk`(27) → **`tool_call`**(status=pending) → **`tool_call_update`**×6（in_progress 流式 rawInput → completed 带完整 stdout）→ thought → `agent_message_chunk`(4) → response `end_turn`。
- tool_call 字段完整：`toolCallId / title("Bash") / kind("execute") / status / rawInput / content`。
- `plan` notification 未观测到（未进 plan mode 的 turn 不产生）。
- 证据：`evidence/probe2-prompt.transcript.ndjson`、`evidence/probe3a-updates.json`。

### Q5. session/load resume 回放 — PARTIAL

流程：phase A 建 session 发一个 tool turn → 断开进程；phase B 新 ACP 进程 initialize + `session/load { sessionId, cwd, mcpServers }`。

- **回放确实发生**：load 响应（含 configOptions）之后，历史以 `session/update` 推送。
- 回放序列（tool turn）：`user_message_chunk`（完整用户原文）→ `agent_thought_chunk`（仅第 1 条 thought）→ `tool_call`（status=in_progress，完整 rawInput）→ `tool_call_update`（completed，完整输出）→ `available_commands_update`。
- **fidelity 缺口（实测两处，均有 raw transcript 佐证）**：
  1. **assistant 最终文本不回放**：`agent_message_chunk` 在回放中出现 0 次。对纯文本 session（probe2 的 PONG turn）交叉验证同样缺失——即 **resume 后 UI 无法从回放重建 assistant 消息正文**。
  2. **thought 被压缩**：live 27 条 thought chunk，回放仅 1 条。
- 回放中 toolCallId 前缀从 live 的 `0:` 变为 `1:`（turn 序号语义，不影响内容）。
- 补测 `session/resume`：响应与 load 类似但**不回放任何历史**（仅 `available_commands_update`）——轻量 attach 语义。`session/list` 可用，返回 `{ sessionId, cwd, title, updatedAt }` 数组。
- 定性：这是"**resume 自身 history**"（同一 CLI 自己写的 session 原样读回），不是 arbitrary import；user/tool 内容完整，assistant message 正文丢失。
- 证据：`evidence/probe3b-resume.transcript.ndjson`、`probe3b-replay-updates.json`、`probe3c-replay-*.json`、`probe6-list-resume.transcript.ndjson`。

### Q6. Provider/Model 边界 — PASS

- ACP surface **有 model selection**，三条路径实测：
  - `session/new` 传 `model` 字段 → **被静默忽略**（currentValue 仍 default），非有效路径。
  - **`session/set_model { sessionId, modelId }` → 生效**，响应 `{}` 并推 `config_option_update`。
  - **`session/set_config_option { configId: "model", value }` → 生效**，响应含完整 configOptions。
- 但可选范围**仅限 CLI 自身 config.toml 里声明的 model alias**（本机 3 个，均来自 `~/.kimi-code/config.toml`）。ACP 不提供 provider 定义、API key、base URL 的任何入口。
- **结论：provider 配置仍完全由 CLI config 管理**，ACP 只能在"已注入 home 的 alias 集合"内切换。
- **支持 mossx 设计假设**：Runtime Binding 继续负责 provider 隔离——沿用既有 `KIMI_CODE_HOME` per-provider 物化方案（openspec/specs/kimi-engine-runtime 已规约），ACP adapter 只需在 spawn 时注入对应 `KIMI_CODE_HOME`，再用 `session/set_model` 选 alias 即可。
- 证据：`evidence/probe5-model.transcript.ndjson`。

### Q7. 长 turn request 语义与 ACK 映射 — PASS（语义确认）

- `session/prompt` 的 response **在整个 turn 结束后才返回**（probe2：+4633ms，在所有 chunk 之后；probe4 cancel 场景 +6024ms）。Prompt Accepted 与 Completion **不解耦**，无独立的 "accepted" 信号。
- turn 期间唯一的近即时信号是 session 级 `available_commands_update`（+6ms，与 prompt 无因果关系）。
- ACK 阶段映射结论：

| ACK 阶段 | 信号来源 | 强度 |
|---|---|---|
| Prompt Accepted | 仅"request 未立即报错" + 等待首个 chunk | **inferred（弱）** |
| First Token / Working | 首个 `agent_thought_chunk` / `agent_message_chunk` / `tool_call` | **真实信号（强）** |
| Tool 执行进度 | `tool_call` / `tool_call_update`（pending→in_progress→completed/failed） | **真实信号（强）** |
| Completion | prompt response + `stopReason`（end_turn/cancelled/…） | **真实信号（强）** |

相对现有 prompt adapter"全程无显式信号、terminal 靠 process exit 推断"，ACP 把后三个阶段全部升级为真实信号，只有 Accepted 仍是 inferred。

### Q8. 取消 — PASS

- 存在 **`session/cancel`（notification，无 response）**。
- 实测：首个 chunk 到达后发送 cancel，prompt request 以 **`{ "stopReason": "cancelled" }`** 返回；cancel 后仍有 8 条 in-flight `agent_thought_chunk` 刷出（发送方 pipeline 残留，adapter 需在 terminal 后丢弃迟到 chunk）。
- 证据：`evidence/probe4-cancel.transcript.ndjson`。

### Q9. Capability Cache Key identity — PASS

见第 1 节表格：binary path + version + sha256 + ACP protocolVersion=1 全部可直接采集。建议 cache key 额外纳入 `agentCapabilities` 的 JSON hash（initialize 每次首连都要做，成本为零）。

## 3. Go / No-Go 结论

### 结论：**GO**（有保留项）

Kimi 0.27.0 的 ACP 是**功能完整的 stdio ACP server**：握手、session 生命周期、流式 chunk、tool 可视化、cancel、model 切换、session 持久化同源全部实测通过。ACK 四阶段中三阶段可拿到真实信号，相对现有 prompt adapter（ackFidelity = weak，terminal 靠 exit 推断）是质变升级。保留项仅 replay fidelity（下述 R1）。

### ACK 阶段映射表（adapter 设计输入）

| mossx ACK 阶段 | ACP 信号 | 备注 |
|---|---|---|
| Prompt Accepted | prompt request 未立即 error + 无显式信号 | inferred，与 Codex app-server 相当 |
| Working / First Token | 首个 `agent_thought_chunk`/`agent_message_chunk`/`tool_call` | 真实 |
| Tool Progress | `tool_call` + `tool_call_update`（含 rawInput、stdout content） | 真实，fidelity 高于 stream-json |
| Completion | prompt response `stopReason` ∈ `end_turn` / `cancelled` / `refusal` / `max_tokens`（后两者未实测，按 schema 枚举） | 真实 |
| Interrupt | `session/cancel` notification → `stopReason: "cancelled"` | 真实 |
| Resume | `session/load` replay 或 `session/resume` attach | 真实，但 assistant 正文缺失（R1） |
| Model Binding | `session/set_model` / `set_config_option`，provider 由 `KIMI_CODE_HOME` 注入 | 真实 |

## 4. 已知风险与待 Wave 5 复核事项

- **R1（中）replay 缺 assistant message**：`session/load` 回放不含 `agent_message_chunk`，thought 也被压缩。影响：resume 后 UI 无法从 ACP 回放重建助手气泡。mossx 自身有持久化 transcript（realtime reducer 落盘），可用本地历史渲染 + ACP 仅作 runtime attach 来规避；若未来依赖 ACP replay 渲染，需要 Kimi 修复。**待 Wave 5 复核新版本是否补齐。**
- **R2（低）非标扩展依赖**：`sessionCapabilities.list/resume`、`authMethods` 的 terminal-auth `_meta`、`configOptions` 机制是 ACP 草案/Kimi 扩展，跨版本字段名可能漂移；adapter 需做 capability-guarded 降级（缺 list 则回退 `session_index.jsonl` 扫描，与现状一致）。
- **R3（低）cancel 后迟到 chunk**：cancel 确认前仍有 in-flight chunk 推送，adapter 必须在 terminal 态丢弃同 session 迟到 update，避免污染已结算的 turn。
- **R4（低）permission 链路未实测**：本次以 client 自动 allow + yolo mode 绕过。生产 adapter 需实现 `session/request_permission` ↔ mossx 审批 UI 的桥接，行为（option kind、cancel outcome）待 Wave 1/2 实测。
- **R5（低）`stopReason` 枚举覆盖不全**：仅实测 `end_turn`、`cancelled`；`refusal`、`max_tokens`、`max_turn_requests` 未触发，adapter 按 schema 枚举兜底即可。
- **R6（提示）未验证版本协商降级**：仅测试 protocolVersion 1→1。未来 Kimi 升级 ACP v2 时需复核协商行为（cache key 含 protocolVersion 已为此兜底）。
- **R7（提示）ACP 与 stream-json 双轨**：ACP adapter 落地前，现有 `kimi.rs` prompt adapter 保持 `ackFidelity = weak` 显式标注，不做能力冒充；两条 track 的 canonical sessionId 同源（`session_*`），迁移不破坏 history 关联。
